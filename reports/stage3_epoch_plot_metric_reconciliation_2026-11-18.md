# Stage-3 epoch-plot metric reconciliation

Date: 2026-11-18

## What was fixed

The Stage-3 target-speaker KWS figure had been easy to misread because its
epoch-history F1 curve was compared directly with the 97.40% KWS value in the
paper. The figure is now explicitly titled **Target-speaker KWS epoch history
at fixed validation threshold 0.50**. Its validation panels also include the
threshold in their titles and legends.

The corrected artifacts are:

- `reports/figures/stage3_target_kws_negative_calibrated_comparison_2026-10-16.png`
- `reports/figures/stage3_target_kws_negative_calibrated_comparison_2026-10-16.pdf`
- the same two files in `reports/paper_figures_latest_2026-10-20/`

## Why the epoch F1 is around 0.7

The Stage-3 trainer evaluates each epoch with `argmax` over the two output
classes. For this binary model, that is the fixed 0.50 probability operating
point. The logged validation split has 1,629 examples and is negative-heavy.
The source JSONL histories contain only `train_accuracy` and fixed-point
validation accuracy, precision, recall, and F1. They do not contain per-epoch
probability scores, threshold sweeps, or training loss.

The maximum F1 values actually present in the two plotted histories are:

| Run | Best epoch | Fixed-point validation F1 |
|---|---:|---:|
| Previous large | 9 | 66.67% |
| Negative calibrated | 3 | 70.36% |

These are valid epoch metrics for those runs. Raising the plotted curve to
0.90+ would be unsupported by the recorded data.

## Where the 97.40% value comes from

The paper's 97.40% value is a separate, narrow TSE-domain operating-point
result. It was obtained after sweeping a detection threshold (the selected
reported point is approximately precision 98.94%, recall 95.90%, F1 97.40%).
It is not a per-epoch F1 value from either history in the epoch figure and it
must not be drawn as though it were one.

The paper already describes this distinction in the Stage-3 table and text:
the value is isolated KWS evidence, not continuous full-pipeline wake
accuracy. The figure now states the distinction directly so a reader does not
interpret the 0.70 epoch curve as a contradiction or the 0.974 operating point
as a training epoch.

## Reproducibility

The figure is generated by:

```powershell
python scripts/reporting/plot_stage3_target_kws_history.py `
  --history 'previous_large=logs/stage3_target_kws_gsc_marvin_hardneg_aishell5_smart_speaker_large_candidate/epoch_metrics_810d83a90edb4a4186ddb89fa3ddb77f.jsonl' `
  --history 'negative_calibrated=logs/stage3_target_kws_gsc_marvin_hardneg_aishell5_smart_speaker_negcal_balanced_ft2_2026-10-16/epoch_metrics_a4e3ac9e626b49f8ba48c873c3719a47.jsonl' `
  --output reports/figures/stage3_target_kws_negative_calibrated_comparison_2026-10-16.png `
  --pdf-output reports/figures/stage3_target_kws_negative_calibrated_comparison_2026-10-16.pdf
```

To produce a genuine epoch curve above 0.90, the model would need to be
re-evaluated and logged at each epoch with the same threshold-sweep protocol,
or the training would need to be repeated while saving per-epoch checkpoints
and raw validation scores. That result would still need to be reported as a
different protocol from the fixed-threshold epoch history.
